# Эксплуатация SaleScout

## Границы текущей версии

Это небольшой SaaS с реальными аккаунтами и постоянным хранением. Поддерживается **один экземпляр приложения** и PostgreSQL. Лимиты запросов хранятся в памяти приложения; перед горизонтальным масштабированием нужен общий rate-limit store. Redis, биллинг, роли сотрудников, интеграция с Kaspi, автоматический сбор цен и юридические документы оператора не входят в эту версию.

Для публичного запуска владелец проекта задаёт домен, SMTP, контакты поддержки и собственные условия использования/политику обработки данных. Репозиторий не подставляет выдуманные сведения об операторе.

## Конфигурация

| Переменная | Значение |
| --- | --- |
| `NODE_ENV` | `production` для публичного запуска |
| `APP_ORIGIN` | Точный публичный HTTPS origin без пути |
| `DATABASE_URL` | Строка подключения к PostgreSQL |
| `SESSION_SECRET` | Уникальный случайный секрет, не менее 32 символов |
| `HOST`, `PORT` | Интерфейс и порт приложения |
| `TRUST_PROXY` | `1` только за единственным доверенным прокси; иначе `0` |
| `SMTP_HOST`, `SMTP_PORT` | Сервер отправки писем |
| `SMTP_SECURE` | `true` для implicit TLS, обычно порт 465 |
| `SMTP_USER`, `SMTP_PASS` | SMTP-учётные данные |
| `SMTP_FROM` | Подтверждённый адрес отправителя |
| `DOMAIN` | Домен для Caddy/production Compose |
| `POSTGRES_PASSWORD` | Пароль контейнера PostgreSQL |

Не публикуйте `.env`. `npm run setup` генерирует секреты, не выводя их в терминал. При переносе PostgreSQL на внешний сервер используйте защищённое соединение и доверенный CA; не отключайте проверку сертификатов.

## Реализованные меры

- Пароли: scrypt с отдельной случайной солью, N=32768, r=8, p=1. Проверка через timing-safe comparison.
- Сессии: PostgreSQL, HttpOnly, SameSite=Lax; Secure и `__Host-` cookie в production. Вход регенерирует идентификатор сессии. Cookie живёт до 7 дней.
- Изменяющие запросы `/api` проверяют CSRF-токен и, когда присутствует, Origin. Исключение — POST callback Apple: он только временно сохраняет код; вход происходит после одноразовой проверки state и исходной браузерной сессии на GET callback. Секреты сессии не доступны клиентскому JavaScript.
- Почтовые токены — случайные 256-битные значения; в БД хранятся только SHA-256 хеши. Подтверждение действует 24 часа, восстановление — 30 минут. Использование одноразовое.
- Почтовая ссылка передаёт токен во фрагменте URL, который убирается из адресной строки после открытия. Приложение не записывает тела запросов в access-log.
- Сброс пароля повышает версию авторизации и удаляет старые сессии. При каждом доступе к каталогу пользователь заново проверяется в БД.
- Все пользовательские значения передаются в SQL параметрами. Идентификатор владельца берётся из сессии, а не из тела запроса.
- По умолчанию до 180 запросов в минуту с IP и до 30 запросов авторизации за 15 минут. Повторное письмо одного вида одному аккаунту — не чаще раза в минуту.
- Helmet/CSP, запрет встраивания во фреймы, `no-store` для приватных API. Запросы ограничены 1 МБ.
- Production-контейнер работает от пользователя `node`, с read-only файловой системой и без Linux capabilities. PostgreSQL и приложение доступны только во внутренней сети Compose.

Эти меры проверяются автоматическими тестами и не являются обещанием полного аудита безопасности. Внешний pentest, нагрузочные тесты и мониторинг реальной инфраструктуры в репозиторий не включены.

## Социальный вход

Настройка: [Google и Apple](docs/OAUTH.md). Секреты доступны только серверу. ID token проверяется по подписи JWKS, issuer, audience, сроку и nonce; Google использует PKCE. Callback одноразовый и привязан к исходной сессии. Данные Apple из неподписанного поля `user` игнорируются. Авторизация по подтверждённой почте не объединяет чужие аккаунты автоматически.

## Резервное копирование

```sh
npm run backup
npm run backup -- --production
```

Выберите одну команду для нужного окружения. Скрипт запускает `pg_dump` и сохраняет бинарный custom-format dump в `backups/`. Незавершённый файл имеет суффикс `.partial` и не считается резервной копией. Команда работает в PowerShell без текстового преобразования бинарных данных.

Копии содержат пользовательские данные и хеши паролей. Храните их вне сервера с ограниченным доступом; установите срок хранения и регулярное расписание. Скрипт не загружает копии в сторонние облака и не удаляет старые файлы.

### Проверка восстановления

Сначала восстановите копию в **новую пустую БД**, а не поверх рабочей. Пример для локального Compose (замените имя файла на свою копию):

```sh
docker compose cp backups/YOUR_BACKUP.dump db:/tmp/salescout.dump
docker compose exec db createdb -U salescout salescout_restore_check
docker compose exec db pg_restore -U salescout -d salescout_restore_check --no-owner --exit-on-error /tmp/salescout.dump
docker compose exec db psql -U salescout -d salescout_restore_check -c "SELECT count(*) FROM users;"
```

Для production используйте `docker compose -f compose.prod.yaml ...`. Перед переключением рабочего приложения на восстановленную БД остановите запись данных и проверьте каталог, пользователей и миграции. Сессии также попадают в dump; при аварийном восстановлении целесообразно завершить их согласно вашей процедуре восстановления.

## Мониторинг и обновление

`/healthz` проверяет процесс, `/readyz` — подключение к PostgreSQL. Docker использует readiness для healthcheck. Логи идут в stdout и содержат request ID, метод, путь, статус и длительность; при внутренних ошибках тот же request ID возвращается клиенту.

```sh
docker compose -f compose.prod.yaml ps
docker compose -f compose.prod.yaml logs --tail=100 app
```

Настройте внешний мониторинг HTTPS/readiness, ошибки 5xx, состояние диска БД и выполнение резервных копий. Перед обновлением сделайте backup; запускаемые миграции сериализованы блокировкой PostgreSQL. Политики автоматического rollback схемы нет — возврат версии после несовместимой миграции требует плана восстановления.

## Проверка перед приглашением пользователей

1. Домен открывается по HTTPS, Caddy получил сертификат.
2. Письма подтверждения и сброса доходят до реальных ящиков.
3. Два разных аккаунта видят только свои товары.
4. После перезапуска приложения каталог и сессия сохраняются.
5. После сброса пароля старые сессии теряют доступ.
6. Резервная копия восстановлена в отдельную тестовую БД.
7. Указаны контакты оператора, подготовлены документы для пользователей и включён мониторинг.

Публикация на реальном домене, доставляемость внешней почты, визуальная проверка целевых браузеров и нагрузочная ёмкость должны подтверждаться в вашем окружении. Локальные HTTP/DOM-тесты не заменяют эти проверки.
